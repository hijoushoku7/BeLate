# BeLate 要件定義書

最終更新: 2026-09-14

## 1. 背景と目的

大学生のグループにおける「集合時間に遅れる人がいる」問題を、**金銭的ペナルティとエンタメ性**で解決する。

遅刻を責める文化はグループの空気を悪くするが、遅刻を放置すると全員の時間が失われる。本アプリは遅刻を「怒られること」から「ネタになること」に変換し、その副作用として遅刻を減らす。

## 2. スコープ

| 項目 | 内容 |
|---|---|
| フェーズ | プロトタイプ（ハッカソン作品 兼 自分たちのグループでの実運用） |
| 主戦場 | LINE Bot（Messaging API） |
| 補助 | LIFF（LINE内Webアプリ）。将来のiOSアプリ化を見据え、ロジックは全てサーバAPIに置く |
| 対象外 | 決済システム、一般公開（アカウント認証申請・プライバシーポリシー整備）、iOSアプリ |

金銭は **表示・記録のみ**。実際の授受はユーザ間で勝手にやってもらう。「払った」ボタンすら作らない。

## 3. 用語

| 用語 | 定義 |
|---|---|
| グループ | Botが招待されたLINEグループ。1つのLINEグループ = 1グループ |
| イベント | 1回の集合予定。日時・場所・罰金設定を持つ |
| 幹事 | そのイベントを作成した人。設定変更の唯一の権限者 |
| 参加者 | そのイベントに「参加」を表明した人 |
| 定時勢 | 集合時刻までに到着判定を得た参加者 |
| 遅刻者 | 集合時刻を過ぎて到着した／到着しなかった参加者 |
| ダウト | 「あいつは遅刻するか」に対する参加者同士の賭け |
| 罰金 | 遅刻者が定時勢に払う額。遅刻時間に比例して増える |

## 4. 支配的制約：LINE無料枠 月200通

本システムの設計を決定づけた最大の制約。

- LINE公式アカウント コミュニケーションプラン（無料）は **月200通**
- Push / マルチキャスト / ブロードキャストは **送信対象の人数分** カウント。5人グループへの1 pushで **5通** 消費
- **応答メッセージ（Reply）はカウントされない**（ユーザ発言に replyToken で30秒以内に返す方式）
- 200通を使い切るとその月は一切配信不可。課金して超過送信する逃げ道もない

### 設計方針

> **Pushは「ユーザが何もしていないのに割り込む」瞬間だけに使う。それ以外は全てReplyで賄う。**

Push予算を **1イベントあたり最大7通** に固定する。

| 通知 | 手段 | 宛先 | 通数(5人グループ) |
|---|---|---|---|
| 集合時刻の到来・罰金カウント開始 | **Push** | グループ | 5 |
| 遅刻催促＋位置共有依頼（1人1回のみ） | **Push** | 未到着者の1:1 | 1〜2 |
| イベント作成完了・参加受付 | Reply | グループ | 0 |
| ダウト受付・結果 | Reply | 1:1 | 0 |
| 到着報告への応答 | Reply | グループ | 0 |
| 精算表（幹事が「精算」と打つ） | Reply | グループ | 0 |
| 戦績（「戦績」と打つ） | Reply | - | 0 |

→ 月およそ **28イベント** まで運用可能。デモ・実運用ともに十分。

超過時は「今月の配信枠を使い切りました」で機能停止する。プロトタイプなので割り切る。

## 5. 技術構成

| レイヤ | 選定 | 理由 |
|---|---|---|
| ランタイム | Cloudflare Workers | 無料枠10万req/日、常時起動不要 |
| フレームワーク | Hono (TypeScript) | Workers向けに軽量 |
| DB | Cloudflare D1 (SQLite) | 無料枠5GB |
| 定期実行 | Workers Cron Triggers | 集合時刻のPush・自動確定に必須。無料 |
| フロント | LIFF（素のHTML+JS、Workerから静的配信） | ビルドツール不要 |
| 署名検証 | Web Crypto API | 標準APIで完結、依存ゼロ |

**注意**: LIFFが属する「LINE Loginチャネル」と Botの「Messaging APIチャネル」は **同一プロバイダー配下** に置くこと。別プロバイダーだと userId が一致せず設計が破綻する。

コストは全て0円。

## 6. 機能要件

### F1. グループ登録

- LINEグループにBotを招待するだけで利用可能。設定作業ゼロ
- `join` イベントで `groupId` を取得し `groups` に登録
- グループ作成時に「ダウト機能を使う／使わない」を選択（合意なきグループでの人間関係事故を防ぐ）

**制約**: LINE APIではBotがグループのメンバー一覧を取得できない（認証済／プレミアムアカウント限定）。したがって「誰が参加者か」はイベントごとの参加表明で確定させる。

### F2. イベント作成

起点は **LINEの位置情報送信**。標準UIをそのまま使うため実装が最小になる。

```
幹事がグループに位置情報を送信
  ↓ Bot が Reply（無料）
「ここで集合ですか？ 日時を選んでください」
  [今日19:00] [今日20:00] [明日12:00] [日時を選ぶ→LIFF]
  ↓
イベント作成完了。参加ボタン＋LIFF URLをReplyで提示
```

- 罰金設定はプリセット3つから選択（LINE UIで自由入力は苦痛）
  - ゆるめ: 初期100円 / 20円per分 / 上限1,000円
  - **標準: 初期200円 / 50円per分 / 上限3,000円**
  - きつめ: 初期500円 / 100円per分 / 上限5,000円
- 細かい調整をしたい場合のみLIFFフォームへ
- **1グループにつき同時に1イベントのみ**。アクティブなイベントがある状態での新規作成は拒否

### F3. 参加登録

- イベント作成時のReplyに「参加」ボタン。押した人だけが対象者
- 参加登録時に **1:1メッセージが送れるか（Bot友だち追加済みか）** を判定
  - 未追加なら参加を保留とし、グループで「友だち追加してね」と案内
  - 理由: ダウト通知・遅刻催促は1:1でしか送れない
- **参加締切 = 集合2時間前**（ダウト締切と同じ）
- 欠席宣言:
  - 締切（2時間前）より前 → 罰金ゼロ
  - 締切以降 → 上限額と同じ扱い。直前キャンセルが最強の逃げ道になるのを防ぐ

### F4. ダウトシステム

| 項目 | 仕様 |
|---|---|
| 誰が | 参加者全員 |
| 誰に | **自分以外の**参加者（八百長防止） |
| 内容 | 「遅刻する」か「遅刻しない」の二択 |
| 掛け金 | 300円固定 |
| 回数 | 1人1対象につき1回のみ |
| 締切 | 集合時刻の2時間前 |
| 秘匿 | 賭けは1:1チャットでのみ行われ、イベント進行中は対象者に知らされない |
| 精算 | 的中者が、外した人の掛け金を山分け。罰金とは別会計 |
| 公開 | **イベント終了後、グループで全公開**（誰が誰に何を賭けたか含む） |

終了後の全公開が本アプリのエンタメの本体。「遅刻中は秘密、精算時に暴露」という時間差がオチになる。ダウト機能を無効にしているグループでは一切動作しない。

### F5. 位置情報共有

**LINEはバックグラウンドで位置を取得できない。** ユーザがLIFFを開いた瞬間しか取れないため、自動追跡は原理的に不可能。

- 共有する情報は **集合地点からの距離のみ**（ETAは出さない。経路APIは有料で、直線距離からの推定は誤解を生む）
- 集合時刻を過ぎた時点で、**未到着者の1:1にのみ** 位置共有依頼をPush（1人1回限り）
- 開いた人の距離がグループに表示される
- 共有は強制できない。開かない人は距離不明のまま罰金だけ増える
- **インセンティブ**: 位置報告をしたときのReplyでのみ「自分にかかっているダウトの途中経過」が見られる。これによりPushなしで位置情報が集まる

### F6. 到着判定

```
Bot「着いたらここから報告 → https://liff.line.me/xxx?e=EVENT_ID」
  ↓ タップ（LINE内ブラウザでLIFF起動）
LIFF: liff.init() → liff.getProfile() で userId 取得（ログイン画面なし）
      navigator.geolocation.getCurrentPosition() で緯度経度
  ↓ POST /api/arrive { eventId, userId, lat, lng }
サーバ: 集合地点との距離を計算 → 判定 → 罰金確定
  ↓ Reply（無料）
Bot「Aさんが到着しました（3分遅刻 / 350円）」
```

- **判定半径: 150m固定**。GPSは屋内・地下・ビル街で50〜200mずれるため、厳しすぎると正直者が損をする
- `liff.sendMessages()` は使わない。クライアントからの申告は改ざん自由なので、判定は必ずサーバ側で行う
- 集合時刻**前**の報告も受け付け、「早着」として罰金ゼロを確定
- **二重報告は冪等**: `arrived_at IS NULL` のときのみ更新
- 地下等で位置が取れない場合の逃げ道として、手動申告＋グループの異議申し立て（人間系）を許容
- GPS偽装対策は行わない。友人グループ前提であり、社会的圧力で足りる

### F7. 罰金計算

```
遅刻分数 = ceil((到着時刻 - 集合時刻) / 60)   // 0以下なら罰金ゼロ
罰金 = min(初期金額 + per分 × 遅刻分数, 上限額)
```

- 標準設定では 初期200円 + 50円/分、上限3,000円（= 56分で上限到達）
- カウントの停止条件:
  1. 到着報告（到着時刻で確定）
  2. 上限額への到達
  3. 幹事の「解散」操作
  4. 集合時刻から3時間経過（自動確定・上限額）

### F8. 精算

- 罰金は **定時勢で山分け**。遅刻者は受け取り側に入らない
- 全員が遅刻した場合は誰も受け取らず、記録のみ残る
- ダウトの精算は罰金と別会計で計算した後、**相殺して1本の債務リストにする**

出力イメージ:

```
【ダウト結果】
 Bさんの遅刻に 3人が賭けていました
  当たり: C, D / はずれ: E
 ...

【精算】
 A → C  1,200円
 B → D    800円
 支払いは各自でお願いします
```

内訳は長くなるだけなので出さない。実用情報は「誰が誰にいくら払うか」だけ。

### F9. 戦績

「戦績」と打つとReplyで返す（無料）。

- 誰が何回遅刻したか、平均遅刻分数、累計罰金
- **集計カラムは持たない。** `participants` テーブルの生データを `GROUP BY user_id` で都度集計する
- 理由: 非正規化した集計値は必ずズレる。データ量は数千行規模で、毎回集計しても一瞬。生データを残しておけば後から指標を足せるが、集計時に捨てた情報は二度と戻らない

## 7. イベントの状態遷移

```
 draft ──幹事が日時確定──▶ open
                            │ 参加募集中 / ダウト受付中
                            │
        ──集合2時間前──────▶ locked
                            │ 参加締切 / ダウト締切
                            │
        ──集合時刻──────────▶ running
                            │ 罰金カウント開始
                            │ ★ 唯一のグループPush発射
                            │
  ┌─全員到着 ─────┐
  ├─幹事が「解散」─┼─────▶ settled
  └─3時間経過─────┘          精算確定 / ダウト結果公開
```

### 変更権限

イベント設定を変更できるのは **幹事（作成者）のみ**。

| 状態 | 集合時刻の変更 | 挙動 |
|---|---|---|
| `open` | 可 | ダウトはそのまま有効 |
| `locked` | 可 | **変更した瞬間に全ダウトを無効化し、掛け金を返す**。Botがグループに「集合時刻が変更されたためダウトは全て無効になりました」と通知（Reply） |
| `running` | **不可** | 罰金カウント中に基準時刻を動かすと計算が壊れる |
| `settled` | 不可 | - |

`locked` 後の時刻変更でダウトを残すと、幹事が集合を後ろにずらして結果を操作できてしまう。無効化はその穴を塞ぐための措置。

`locked` 後の参加追加は不可（ダウトの公平性が壊れるため）。ただしグループの表示は観戦者として見える。

## 8. データモデル (D1 / SQLite)

```sql
CREATE TABLE users (
  user_id     TEXT PRIMARY KEY,   -- LINE userId
  display_name TEXT,
  is_friend   INTEGER NOT NULL DEFAULT 0,  -- 1:1 Push が可能か
  updated_at  INTEGER NOT NULL
);

CREATE TABLE groups (
  line_group_id TEXT PRIMARY KEY,
  doubt_enabled INTEGER NOT NULL DEFAULT 1,
  created_at    INTEGER NOT NULL
);

CREATE TABLE events (
  id         TEXT PRIMARY KEY,
  group_id   TEXT NOT NULL REFERENCES groups(line_group_id),
  owner_id   TEXT NOT NULL REFERENCES users(user_id),  -- 幹事
  place_lat  REAL NOT NULL,
  place_lng  REAL NOT NULL,
  place_name TEXT,
  meet_at    INTEGER NOT NULL,
  state      TEXT NOT NULL,    -- draft/open/locked/running/settled
  base_fine  INTEGER NOT NULL,
  per_min    INTEGER NOT NULL,
  max_fine   INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  settled_at INTEGER
);

CREATE TABLE participants (
  event_id    TEXT NOT NULL REFERENCES events(id),
  user_id     TEXT NOT NULL REFERENCES users(user_id),
  status      TEXT NOT NULL,   -- joining / absent
  joined_at   INTEGER NOT NULL,
  arrived_at  INTEGER,
  arrival_lat REAL,
  arrival_lng REAL,
  late_minutes INTEGER,
  fine        INTEGER,
  PRIMARY KEY (event_id, user_id)
);

CREATE TABLE bets (
  event_id     TEXT NOT NULL REFERENCES events(id),
  bettor_id    TEXT NOT NULL REFERENCES users(user_id),
  target_id    TEXT NOT NULL REFERENCES users(user_id),
  predicts_late INTEGER NOT NULL,  -- 1: 遅刻する
  stake        INTEGER NOT NULL DEFAULT 300,
  payout       INTEGER,
  PRIMARY KEY (event_id, bettor_id, target_id)
);

CREATE TABLE reports (   -- 位置報告の履歴
  event_id    TEXT NOT NULL REFERENCES events(id),
  user_id     TEXT NOT NULL REFERENCES users(user_id),
  lat         REAL NOT NULL,
  lng         REAL NOT NULL,
  distance_m  INTEGER NOT NULL,
  reported_at INTEGER NOT NULL
);
```

`users.is_friend` は参加登録時の1:1送信可否判定に使う。表示名は毎回APIで引くとレート制限に触るためキャッシュする。

## 9. LIFF画面

| 画面 | 用途 |
|---|---|
| 到着報告 | 位置情報を取得してPOST。本アプリのLIFF必須理由 |
| 位置共有 | 未到着者が距離を共有する。到着報告と同一画面でよい |
| イベント設定（裏口） | プリセット以外の罰金設定・日時の細かい指定 |
| 精算結果 | 債務リストの表示 |

ダウトの賭け画面はLIFFにしない。秘匿性の観点から、1:1トーク内のボタン（クイックリプライ）で完結させる方が自然かつ漏れにくい。

**LIFF実装上の注意**
- HTTPS必須。開発時は `cloudflared tunnel` または ngrok
- バックグラウンド実行不可。ユーザがタップした瞬間しか位置は取れない
- LINE外のブラウザで開くと `getProfile()` が使えない。「LINE内からのみ」と割り切る

## 10. 非機能・割り切り

| 項目 | 方針 |
|---|---|
| 認証 | LIFFの `getProfile()` で得た userId のみ。独自認証なし |
| 精度 | GPS誤差は半径150mで吸収。偽装は対策しない |
| 可用性 | Workersの無料枠に依存。SLAなし |
| タイムゾーン | JST固定 |
| テスト | 罰金計算・距離計算・精算ロジックに対する `assert` ベースの自己チェック1本のみ |

## 11. 作らないもの（明示的なスコープ外）

- 決済システム / 支払いの追跡（「払った」ボタンも作らない）
- 独自の認証・アカウント管理
- ダウト掛け金の実在性（架空の点数として扱う）
- 過去イベントの一覧・履歴閲覧画面（戦績のテキスト出力のみ）
- グループ設定画面・管理画面
- 多言語対応
- 自動テストスイート（上記の自己チェック1本を除く）
- Botのグループ退出・再招待のハンドリング
- 幹事が失踪した場合の権限移譲
- 同一グループでの複数イベント同時進行（1グループ1アクティブで回避）

## 12. 既知のリスク

| リスク | 影響 | 対応 |
|---|---|---|
| 月200通の枯渇 | 月末に機能停止 | 予算7通/イベントで管理。超えたら割り切る |
| 位置共有を誰も開かない | 距離情報が集まらず機能が死ぬ | ダウト途中経過を餌にする。それでもダメなら機能ごと落とす |
| ダウト全公開で人間関係が壊れる | 実運用の停止 | グループ単位でダウト機能をOFFにできる |
| Bot未追加者がいる | 1:1通知が届かない | 参加登録時に検出し、参加を保留にする |
| GPSが取れない場所での集合 | 到着報告不能 | 手動申告＋グループの異議申し立てで救済 |
